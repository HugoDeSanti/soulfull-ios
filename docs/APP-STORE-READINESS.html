GATE 1

The build won't upload

All 5 fixed

These fail at validation or at App Store Connect ingestion. None involve product work — they're all configuration, and all of them are an afternoon.

FixedAssets.xcassets/AppIcon.appiconset

There is no app icon

The icon set contains only a Contents.json declaring a 1024×1024 slot with no filename. Confirmed absent from the compiled Assets.car in the Release build, and the built Info.plist has no CFBundleIcons key at all. Upload is refused outright.

FixDrop a 1024×1024 PNG, opaque, no alpha channel into the icon set and add its "filename" to Contents.json. One universal size is enough on iOS 18 — Xcode derives the rest. Optionally add the dark and tinted variants while you're there.
Fixedproject.yml · Info.plist

The launch screen it points at doesn't exist

UILaunchStoryboardName is set to LaunchScreen, but there is no LaunchScreen.storyboard anywhere in the repo and none in the built bundle. An app with no resolvable launch screen renders letterboxed at a legacy resolution instead of full-screen — a visible defect a reviewer will catch even if validation lets it through.

FixDrop UILaunchStoryboardName and use the modern dictionary instead: UILaunchScreen with a UIColorName pointing at a new color set matching Theme.bg (#0b0c07), so the cold-launch frame hands off cleanly into RootView's breathing logo.
Fixedproject.yml → DEVELOPMENT_TEAM

No signing identity

DEVELOPMENT_TEAM is an empty string, so the Release build signs locally with an ad-hoc identity. There's no distribution certificate, no App Store provisioning profile, and com.soulfullgatherings.app has to be registered as an explicit App ID before either can exist.

FixEnroll in the Apple Developer Program, register the bundle ID, set the team in project.yml, xcodegen generate, then let Xcode manage signing. Archive against a real device destination — a simulator archive can't be uploaded.
FixedPrivacyInfo.xcprivacy — absent

No privacy manifest

The app has no PrivacyInfo.xcprivacy. AppSettings reads and writes UserDefaults on every launch, which is a required-reason API, and the app collects email, name, and the onboarding answers. Apple's ingestion mails an ITMS-91053 notice on upload and has been escalating these from warning to rejection.

FixAdd a manifest with NSPrivacyAccessedAPICategoryUserDefaults reason CA92.1, plus your collected-data types. Supabase and Stripe ship their own manifests, so you only declare your own usage.
FixedInfo.plist

No export compliance declaration

ITSAppUsesNonExemptEncryption is missing, so every single upload stops and waits on a manual answer in App Store Connect before the build becomes testable.

FixAdd ITSAppUsesNonExemptEncryption = false. The app uses only HTTPS and platform crypto, which is the exempt case.
GATE 2

A reviewer will reject it

All 7 addressed

Assume the reviewer opens every tab, taps every button, and tries to buy something. These are the places that fall over when they do.

Guideline 2.1 · addressedPracticeViewModel.swift · Models.swift:581

The Practice tab plays Big Buck Bunny

The practice_sessions table does not exist — the REST endpoint returns 404. So PracticeViewModel.load silently falls into PracticeSession.mock(for:) for all three media tracks, and every session streams BigBuckBunny.mp4 from a Google sample bucket or a 15-second stock MP3. All three Massage entries do the same. A reviewer tapping a guided meditation in a wellness app gets a cartoon rabbit.

FixEither create the table (with a for select to anon, authenticated policy — the same trap 0003 already documents), upload real media to the practice-media bucket and seed rows; or cut the three media tracks and Massages from v1 and ship Practice as Journal, Exercises and Recipes, which are real curated content.
Guideline 4.2 · addressedFeatures/Circle/CommunityPlaceholder.swift

A whole primary tab is an empty state

Circle is one of four tabs in the bottom nav and its entire content is the line "Live circles, member directory, and DMs land here next." A tab that advertises unbuilt features is the textbook minimum-functionality rejection.

FixCut the tab to three for v1 and add Circle back when it exists. Shipping three solid tabs reads as finished; four tabs where one is a coming-soon sign reads as a beta.
Guideline 2.1 · addressedModels.swift:314 · RetreatExperienceHubView.swift

Paying for any retreat but Mallorca lands on empty screens

RetreatExperience.curated(for:) matches on the literal string "mallorca" and returns nil for the other six. So a Kyoto purchase — $6,800 — opens a hub whose hero is a hardcoded Image("mb-welcome") of Mallorca, whose pills say "Deposit paid" regardless, with the to-do card hidden, and whose Packing and Guides tiles push to screens that render []: a header and nothing beneath it. This is the worst moment in the app to have a blank screen.

FixFor v1, the honest move is to make Mallorca the only reservable retreat and show the others as "Coming soon" in the catalog. Otherwise you need generic post-booking content plus real empty states, and a per-retreat hero, before any of them can take money.
Review access · addressedRetreatDetailViewModel.reserve()

The reviewer can't reach anything behind the paywall

Reserve goes straight to Stripe's PaymentSheet. In live mode the reviewer cannot complete a real charge, so the checkout, the experience hub, to-dos, packing, guides and the concierge chat are all invisible to them — a large share of the app that they will read as unfinished or non-functional.

FixSupply a demo account in the App Review notes with a paid row pre-seeded in bookings for Mallorca, so signing in flips the CTA to "View your experience" and opens the whole flow. Add a short screen recording of the payment itself.
Guideline 3.1.3(e) · addressedReview notes

Stripe needs to be explained, or it reads as IAP evasion

Using Stripe here is correct — a retreat is a real-world service consumed outside the app, which is explicitly outside the in-app-purchase requirement. But reviewers see a payment sheet that isn't Apple's and reject first. Note that the future membership product is the opposite case: a digital subscription must use StoreKit.

FixState plainly in the review notes that reservations are for physical, in-person retreats at named locations on fixed dates, delivered offline.
Guideline 2.1 · addressedSupabase · retreats

Four of the seven retreats already happened

Live rows: Mallorca began 2026-04-18, Kyoto 2026-05-09, Sedona 2026-06-06, Bali 2026-07-14 — all in the past. Nothing in HomeViewModel or RetreatsViewModel filters by date, so the catalog is selling four trips that are over, and the one retreat with a complete post-purchase experience is among them.

FixFilter to end_date >= today in fetchRetreats(), and reseed with real forthcoming dates. This interacts with the Mallorca-only decision above — if Mallorca is the reservable one, it needs a future date.
Guideline 5.1.1 · addressedRetreatCheckoutView.swift:197

No privacy policy, terms, or support anywhere in the app

Checkout tells the buyer "By reserving you agree to the enrollment terms and cancellation policy" and gives them no way to read either one. There is no privacy policy link, no terms link, and no support contact in any screen — and the app creates accounts and takes payment.

FixAdd a Legal group to the You tab — Privacy Policy, Terms & Cancellation Policy, Contact Support — link the fineprint at checkout to the terms, and host both pages at stable URLs you can also give App Store Connect.
GATE 3

It would pass, but shouldn't ship like this

8 fixed · 2 deferred

None of these will fail review. All of them are things a paying customer hits in the first week.

MoneyStripe dashboard

Stripe is still in test mode

The integration is deployed and verified, but on test keys. Going live needs a fully activated Stripe account (business verification, bank details), live restricted keys with Customers + PaymentIntents + Ephemeral Keys write, a live webhook endpoint, and its signing secret in the function secrets.

FixRun one real low-value live charge end to end and confirm the bookings row lands before you submit — a webhook misconfiguration is silent until someone pays.
MoneyRetreatDetailViewModel.swift:52

The confirmation races the webhook

reserve() sets phase = .reserved the instant PaymentSheet reports .completed, but the bookings row is written asynchronously by stripe-webhook. If that write is slow or fails, the next launch calls loadExistingBooking, finds nothing, and shows "Reserve" again to someone who has already been charged.

FixPoll fetchBooking for a few seconds after success and surface a "confirming your reservation" state, so a missing row is visible rather than silently reverting the CTA.
Money0002_bookings.sql · create-payment-intent

Nothing enforces capacity or prevents a double charge

retreats.max_guests exists but nothing counts bookings against it, so a retreat can be oversold. And bookings has no uniqueness on (user_id, retreat_id) — the same person can pay twice for the same trip, and the app will happily let them.

FixHave create-payment-intent reject when a paid booking already exists for that user and retreat, and when paid bookings have reached max_guests. Both checks belong server-side, next to the price read.
GapFeatures/Profile

There's no "my reservations"

A booking is only visible from inside that one retreat's detail screen. Someone who paid has no list of what they've booked, no receipt, and no way back to their trip except remembering which retreat it was and navigating to it.

FixAdd a reservations list to the You tab reading bookings — it also gives the reviewer an obvious route into the post-purchase flow.
DataSupabase · retreats.group_chat_url

The group chat tile can never appear

group_chat_url is NULL on all seven rows, and the hub only renders the tile if let url — so a documented feature is invisible in production. The mock fallback carries chat.whatsapp.com/REPLACE-WITH-MALLORCA-INVITE, which would open a dead link if the DB fetch ever failed.

FixSet a real invite on the reservable retreat, or pull the tile for v1. Also replace the placeholder in Models.swift — a broken external link in an offline fallback is worse than no tile.
ContentHomeViewModel.swift

Home's programs and circles are hardcoded

The programs table returns 404 and CommunityCircle has no fetch at all, so both shelves are compiled-in mock arrays — including circles with live indicators. As curated content that's defensible; presented as live activity it isn't.

FixEither seed programs and wire the existing unused fetchPrograms(), or reword the shelves so nothing claims to be happening right now.
Dead controlHomeViewModel.tapMood

The mood chips don't do anything

tapMood toggles selectedMood and nothing reads it. The chips are the first interactive thing on the home screen and they lead nowhere.

FixHave the selection filter the ritual card or the practice suggestion — or remove the row. A control that responds but does nothing is worse than no control.
ResilienceAuthManager.swift · RootView.swift

Auth failure is completely silent

If anonymous sign-in fails at launch — no network, or the Supabase project asleep — state becomes .failed and nothing in the UI ever shows it. The app proceeds into mock data, and the user only discovers there's no session when Reserve throws a raw error string at them.

FixSurface .failed as a quiet retry banner, and make the offline copy honest rather than presenting sample retreats as the live catalog.
Accessibility4 of 50 files

VoiceOver has almost nothing to read

Eight accessibility modifiers exist across the whole codebase, in four files. On a UI built from full-bleed photography, glass, and custom-drawn controls, that leaves most of the app unlabelled — including the custom bottom nav and the entire checkout.

FixLabel the bottom nav, the Reserve CTA, the checkout summary, and the checklist rows at minimum. Apple spot-checks this, and it's the one item here that also carries legal weight in several markets.

Debug logging ships in Release

Bare print() calls in HomeViewModel, RetreatsViewModel, PracticeViewModel and AuthManager are compiled into the shipping binary and write to the device console, including auth error detail.

FixMove them behind #if DEBUG or onto Logger with a privacy-aware category.

Paperwork that lives outside the repo

None of this is code, all of it is required, and it's the part that reliably adds a week if you start it late. The privacy labels in particular need a decision you should make deliberately.

Account & identifiers

  • Apple Developer Program enrollment — a D-U-N-S number if you enroll as a company, which alone can take days
  • Register com.soulfullgatherings.app as an explicit App ID
  • Create the app record in App Store Connect
  • Distribution certificate and App Store provisioning profile

Store listing

  • Name, subtitle, promotional text, full description, keywords
  • Support URL and marketing URL — support URL is mandatory
  • Privacy policy URL — mandatory, and must actually resolve
  • Screenshots at 6.9″ and 6.5″, portrait, 3–10 each
  • Category — Health & Fitness or Lifestyle
  • Age rating questionnaire

Privacy nutrition labels

  • Contact info — email, name
  • Identifiers — Supabase user ID, Stripe customer ID
  • Purchases — reservation history
  • Health & Fitness — the onboarding body-state and intention answers most likely fall here; classify them deliberately rather than by accident
  • Stripe's own collection, declared as a third-party partner

Rights & compliance

  • Licensing for the retreat photography — Apple asks for proof if the imagery looks stock or editorial
  • Geist is OFL, so the fonts are clear
  • Export compliance answer, matching the plist key
  • Demo account credentials plus review notes covering Stripe and the seeded booking

Already handled — don't redo these

Worth stating explicitly, because several are the items teams most often panic about late.

5.1.1(v)

In-app account deletion is built and reachable

The You tab offers Delete account behind a confirmation dialog, routed through the delete-account Edge Function, which removes the Stripe customer and the auth user and cascades to profiles and bookings. This is the compliance item most apps get rejected for.

Guideline 5.1.1

The app is fully browsable without an account

Anonymous guest sessions mean nothing is gated behind registration except payment, which is the correct exception. Forced sign-up is a common rejection you've already avoided.

Guideline 4.8

Sign in with Apple is not required

4.8 only triggers when an app offers a third-party or social login. Email/password alone is exempt, so the unbuilt Apple sign-in is a roadmap item, not a submission blocker.

Security

Secrets and payment authority are server-side

Secrets.xcconfig is gitignored and untracked. Stripe keys exist only in function secrets — even the publishable key is returned by the function. The client never writes payment state, prices are read authoritatively server-side, and bookings is written only by the webhook under the service role.

Security

Row-level security is correct on every live table

profiles is scoped to auth.uid() = id with no client write to stripe_customer_id; bookings is read-only for its owner with no insert policy at all; retreats grants select to both anon and authenticated, which is the anonymous-role trap already solved in migration 0003.

Build

The Release build is clean

Compiles at Swift 6 with zero code warnings. The only warning in the log is the benign "no AppIntents.framework dependency" note.

Config

Orientation, deployment target and appearance are consistent

Portrait-only, iOS 18 minimum, dark mode forced at the scene level — no conflicting declarations between project.yml and Info.plist, and no iPad claims to honor.

The order I'd do it in

Enrollment is the long pole and gates everything else, so it starts today regardless of where the code is.

01Start Apple Developer enrollment now. D-U-N-S verification is the one item you cannot compress, and nothing else can be uploaded until it clears.
02Clear Gate 1 in a single pass — icon, launch screen, signing, privacy manifest, export compliance. It's configuration, and it makes the build uploadable.
03Make the scope decision. Cut the Circle tab, and decide whether Practice ships with real media or without the media tracks. Both are subtractions, and both remove a rejection.
04Make exactly one retreat truly reservable — future dates, curated post-purchase content, capacity and duplicate checks — and mark the rest coming soon. This is the largest remaining piece of product work.
05Write and host the privacy policy and terms, then link them from the You tab and from the checkout fineprint. Slow to draft, trivial to wire.
06Take Stripe live and run one real charge end to end, confirming the bookings row arrives.
07TestFlight on a physical device before submitting. The Metal shaders, the glass, and the PaymentSheet all behave differently off the simulator.
08Seed the demo account with a paid Mallorca booking, write the review notes explaining the Stripe classification, and submit.
